#### 🔒 [notification-reliability-lab](https://github.com/Elian-bang/notification-reliability-lab)

운영 장애를 재현해서, **네 가지 처방 중 무엇이 실제로 들었는지** 쟀습니다.

배치가 콘텐츠 3건을 한 트랜잭션에 넣고 돌렸습니다. 첫 건은 자기 일이 72초 만에 끝났고
완료 표시도 그때 했지만, **커밋은 나머지 두 건까지 끝난 뒤였습니다.** 그 행이 99초 잠겼고,
푸시를 받고 들어온 사용자가 그 구간에 도착했습니다.

처방 4개를 각각 3회씩 재현했습니다.

| 처방 | 조회 성공 | 실패 |
|---|---:|---:|
| 조치 전 | 882 | 3 |
| 완료 표시를 건별 커밋 | **2,377** | **0** |
| 조회수 갱신 분리 | 832 | 3 |
| 커밋 후 푸시 | **2,333** | **0** |
| lock timeout 단축 | 865 | 3 |

**넷 중 둘만 들었습니다.** 그리고 진짜 피해는 실패 3건이 아니라 **처리량 2.7배**였습니다.
p95 응답시간(174~208ms)에는 이 장애가 **아예 안 나타났습니다.**

> 얻은 것 — 트랜잭션을 잘게 쪼개는 것만으로는 안 풀립니다.
> 문제는 길이가 아니라 **락을 잡는 문장과 커밋 사이의 거리**였습니다.

#### 🛡️ [backend-guardrails](https://github.com/Elian-bang/backend-guardrails)

리뷰어 경험에 의존하던 규칙을 **CI가 막게** 만드는 실험입니다.
위 장애에서 나온 규칙을 사람이 매번 기억하는 대신 기계가 잡게 했습니다.

규칙을 만들었다고 끝이 아니라, **세 가지를 따로 잽니다.**

| | 무엇을 재나 | 지금 |
|---|---|---|
| ① 탐지 | 위반을 잡는가 | 6개 규칙 전부 |
| ② **오탐** | 정상 코드를 잘못 잡는가 | 8개 경계 사례에 0건 |
| ③ **차단** | merge가 실제로 막히는가 | `BLOCKED` → `CLEAN` 한 쌍으로 확인 |

여기에 **규칙을 테스트하는 테스트**를 따로 둡니다. 규칙이 조용히 죽는 걸 막기 위해서입니다.
첫 실행에서 바로 하나를 잡았습니다. 규칙은 Controller **클래스**의 `@Transactional`을 보는데,
위반 예시는 **메서드**에만 붙어 있었습니다. 규칙이 한 번도 검증되지 않은 채 초록불이었던 겁니다.
앱 검사만 돌렸으면 몰랐습니다. ([커밋 기록](https://github.com/Elian-bang/backend-guardrails/commit/dad9ad4))

못 잡는 것도 표에 같이 씁니다 — ArchUnit이 호출을 한 단계만 보기 때문에
간접 호출 4건은 `KNOWN_GAP`으로, 규칙 없는 항목 2개는 `미구현`으로 표시됩니다.

> **한계** — bad fixture가 규칙당 1개라, 저 `100%`에는 신뢰구간이 없습니다.
> 30개까지 늘리는 게 다음 할 일입니다.

#### 🧵 [virtual-thread-lab](https://github.com/Elian-bang/virtual-thread-lab)

"I/O 바운드니까 Virtual Thread"라고 답해 왔는데, **얼마나 좋아지는지 숫자가 없었습니다.**
그래서 1 core · 1GB에서 조건 26개를 3회씩, 78회 쟀습니다. 그 답은 절반만 맞았습니다.

| 작업 | 플랫폼 스레드 | 가상 스레드 |
|---|---:|---:|
| DB 안 씀 · 동시 500 | 3,585 | **7,138** |
| DB 씀 · 동시 100 · 커넥션 풀 50 | **1,109** | 86.6 |

<sub>TPS · 3회 중앙값</sub>

**DB를 안 건드리면 2배 빠르고, 건드리면 12.8배 느렸습니다.**
가상 스레드는 커넥션을 **한 번도 기다리지 않았는데**(0.0ms) 느렸습니다. 병목은 커넥션 풀이 아니라 **캐리어**였습니다.
CPU는 1개 그대로 두고 캐리어만 1 → 32로 늘리자 86.6 → **614.2**(7.1배). 그래도 플랫폼 스레드(1,109)에는 못 미칩니다.
pinning 스택은 JDBC 드라이버의 소켓 대기(`NioSocketImpl.park`)를 가리켰습니다.

> 얻은 것 — "I/O 바운드니까"로는 부족합니다. 그 I/O를 **누가** 하느냐가 가릅니다.

처음 잰 값은 회차마다 10배씩 튀었습니다. 원인은 전부 측정 도구 쪽이었고,
그걸 어떻게 알아챘는지도 저장소에 같이 남겼습니다.

> **한계** — 1 core와 드라이버 하나(Connector/J 8.3.0)만 쟀습니다.
> `synchronized` pinning이 풀리는 Java 24는 재지 않았습니다.
